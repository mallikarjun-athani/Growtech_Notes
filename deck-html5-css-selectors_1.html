Part 1 · HTML5 tags

What HTML5 actually changed

HTML5 was not a new syntax. It was a new vocabulary — plus the ability to do natively what previously needed a plugin.

Before HTML5

Everything was a div

<div id="header">
<div id="nav">
<div id="content">
<div id="footer">

The id carried the meaning — but only for the developer. The browser, Google and screen readers saw four identical boxes.

With HTML5

The element carries the meaning

<header>
<nav>
<main>
<footer>

Same layout, same CSS effort. But now the meaning is machine-readable — landmarks for assistive tech, structure for search engines.

The one-line summary: HTML5 moved meaning out of your naming convention and into the language itself.

Part 2 · Attributes

Attributes configure an element

An attribute always lives in the opening tag and is written as name="value". They fall into four groups worth naming separately.

Group 1 · Specific

Only meaningful on certain elements

href on a link · src and alt on an image · type on an input · colspan on a cell.

Group 2 · Global

Valid on every element

id · class · style · title · lang · hidden · tabindex · contenteditable · draggable

Group 3 · Boolean

Present or absent — no value

required · disabled · checked · readonly · multiple · autofocus

Group 4 · Custom

Your own data, legally

data-* — anything after data- is valid HTML and readable from JavaScript via dataset.

The boolean trapdisabled="false" still disables the element. Boolean attributes are read by presence, never by value. To enable it, remove the attribute entirely.
Part 2 · Attributes

data-* — the professional way to attach data

markup 
<button
  class="add"
  data-product-id="8842"
  data-price="2499"
  data-in-stock="true">
  Add to cart
</button>
reading it in JavaScript 
// note the camelCase conversion
btn.dataset.productId   // "8842"
btn.dataset.price       // "2499"
btn.dataset.inStock     // "true"

// every value is a STRING
Number(btn.dataset.price) + 1  // 2500
btn.dataset.price + 1         // "24991"
Do

Small hooks

An id, a state flag, a config value the JavaScript needs to find.

Don't

Anything private

It is fully visible in DevTools. Never a price the server trusts, never a role or permission.

Part 3 · CSS

CSS is three things in a row

Vocabulary matters in interviews. "Rule" is the whole block. "Declaration" is one property–value pair. "Selector" is the part before the brace. Most candidates call all three "the CSS".
Part 3 · CSS

Three ways to attach CSS

1 · Inline

On the element

<p style="color:red">Hi</p>

Highest priority, zero reuse, impossible to override without !important. Used by JavaScript at runtime and in HTML email.

2 · Internal

In a style block

<style>
  p { color: red; }
</style>

Styles one page only. Useful for critical above-the-fold CSS. Cannot be cached separately from the page.

3 · External

A separate file

<link rel="stylesheet"
      href="main.css">

One file styles a thousand pages. Downloaded once, then cached. The professional default.

Why external really wins: it is not about tidiness. The browser caches that file, so page two of your site loads it from disk instead of the network. Inline styles are re-downloaded with every single page, every single time.
Part 3 · CSS

Which one wins? Not what most people think

Nearly everyone answers "internal beats external, because it is closer to the element". That is wrong.

the actual rule 
/* internal and external have the
   SAME weight. Order decides. */

<style> p { color: blue; } </style>
<link rel="stylesheet" href="a.css">

/* a.css says p { color: green }
   → the text is GREEN.
   The link came last. */
  • Inline beats both — it is attached directly to the element.
  • Internal and external are equal. Whichever appears later in the document wins.
  • !important overrides all of it — which is exactly why it should be a last resort.
  • When two rules have the same weight and the same specificity, the last one written wins.
Ask the room before revealing: "A style block says blue. A linked stylesheet below it says green. What colour is the text?" Most will say blue. The correct answer is green — and the reason is order, not location.
Part 4 · Selectors

Four selectors do most of the work

NameSyntaxSelectsTypical use
Universal*Every single elementA global reset at the top of a stylesheet
Typep, h1, buttonEvery element of that kindBase styling — all paragraphs, all links
Class.btnEvery element carrying that classThe workhorse. Reusable, unlimited
ID#headerThe one element with that idRare in styling. Mostly for JS and anchors
all four together 
/* universal — reset everything */
* { margin: 0; box-sizing: border-box; }

/* type — every paragraph */
p { line-height: 1.6; }

/* class — reusable, use this one */
.btn { padding: 10px 18px; }

/* id — unique, avoid for styling */
#hero { min-height: 400px; }
Use constantly

Class selectors

One element can carry many classes. One class can style a thousand elements. This is how real stylesheets are written.

Use sparingly

ID selectors

An id can only ever apply once, and its specificity is so high it becomes painful to override later.

Part 4 · Selectors

Specificity — the scoring system

When two rules target the same element and both could apply, the browser scores them. Higher score wins, regardless of order.

Part 4 · Selectors

The universal selector, used properly

the reset almost every project starts with 
*,
*::before,
*::after {
  margin: 0;
  padding: 0;
  box-sizing: border-box;
}

That highlighted line is the important one. It changes how width is calculated — from "content only" to "content plus padding plus border", which is how every human expects it to work.

Without border-box

width: 200px + 20px padding

Actual rendered width: 240px. Your three 33% columns overflow the row and wrap.

With border-box

width: 200px + 20px padding

Actual rendered width: 200px. Padding grows inward. Layouts stop fighting you.

Performance note: * is fine in a reset. Using it for real styling — * { transition: all .3s } — makes the browser process every element on the page and is a genuine performance mistake.
Part 4 · Selectors

Class naming that survives the project

Names that break

Describing appearance

.red-text { color: red; }
.big-font { font-size: 24px; }
.left-box { float: left; }

The day the brand changes to blue, you are editing a class called .red-text to make things blue. Now the name lies.

Names that last

Describing purpose

.alert      { color: red; }
.page-title { font-size: 24px; }
.sidebar    { float: left; }

Change the colour and the name still tells the truth. Name the job, never the look.

Interview question hidden here: "How do you organise CSS on a large project?" Mentioning purpose-based naming and a convention like BEM (.card__title--featured) immediately signals you have worked on something bigger than a college project.
Wrap-up

The eight things to carry forward

  • HTML5 gave meaning, not new syntax — header, nav, main, article, section, aside, footer.
  • Article vs section: could it stand alone somewhere else?
  • Input types are free usability — the right one changes the keyboard and validates for you.
  • Boolean attributes are read by presence. disabled="false" still disables.
  • data-* is the only legal way to attach your own data — and it is never private.
  • External CSS wins because it is cached, not because it is tidier.
  • Internal and external are equal — the later one wins.
  • Style with classes. Ids and !important are debts you repay later.
