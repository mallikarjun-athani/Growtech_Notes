Module 04

Flexbox · Position · Grid · Media queriesPutting things where you want them

Four systems, and each one answers a different question. Flexbox arranges along a line. Grid arranges in two directions at once. Position takes an element out of the flow entirely. Media queries change the answer at a different screen size. Knowing which question you are asking is most of the skill.

Part 1 · Flexbox

One idea. Everything else follows from it.

Flexbox has two axes. Every property either works along the main axis or across the cross axis — and which is which is decided entirely by flex-direction. Learn this and you never guess between justify and align again.

The sentence to make them repeat: "justify works along the main axis, align works across it." Not "justify is horizontal" — that is only true by accident, in a row.

Part 1 · Flexbox

The centring answer, and why it is only two lines

.box {
  display: flex;
  justify-content: center;  /* main  → horizontal */
  align-items: center;      /* cross → vertical   */
}

For two decades "how do I centre a div vertically" was the most-asked question on the web. This is the answer. It works at any size, with any amount of content, without knowing the height of anything.

The container needs a height. If the parent is only as tall as its content, there is no vertical space to centre within — and nothing appears to happen. That is the usual reason this "doesn't work".

Wrapping — and the property everyone forgets

  • By default flex refuses to wrap. Items shrink below their natural size instead — which is why a navbar squashes into unreadable slivers on a phone rather than stacking.
  • flex-wrap: wrap is one word that makes most layouts responsive before you write a single media query.
  • align-content is not align-items. It positions the lines as a group, and it does nothing at all unless the items have actually wrapped onto more than one line.
The shorthand: flex-flow: row wrap sets direction and wrap together.
The single most common flex bug: a long word or an image refuses to shrink and pushes the layout sideways. A flex item will not shrink below its content's minimum size unless you tell it to — add min-width: 0 to the item.

Part 1 · Ordering

order — and the accessibility trap under it

The DOM order, unchanged 
<div>A</div>
<div>B</div>
<div>C</div>
With order applied
Aorder: 3
Border: 1
Corder: 2

Default is 0. Lower numbers come first. Negative values are legal, so order: -1 pulls one item to the front without touching the others.

This is the part that gets skipped, and it matters.

order changes only what is painted. It does not change the document. So:
  • A screen reader still reads A, B, C — the visual order is invisible to it.
  • Tab moves focus A → B → C, so keyboard focus appears to jump around the screen at random.
  • Copying the text still gives A B C.
The rule professionals follow: use order for presentational reshuffling only — a sidebar that moves below the article on a phone, where reading order barely changes. If the reading order genuinely differs, change the HTML, not the CSS.
Exam-ready answer: "order and flex-direction: row-reverse both change visual order without changing DOM order, so both decouple the visual sequence from the focus and reading sequence."

Part 2 · Position

Positioned against what? — the question that decides everything

Four of the five values take top, right, bottom, left. What changes between them is what those offsets are measured from. Get that straight and position stops being mysterious.

ValueOffsets measured fromStill takes up space?Scrolls with the page?
staticNothing — offsets are ignored entirelyYesYes
relativeWhere it would have beenYes — its original space is keptYes
absoluteThe nearest positioned ancestorNo — removed from the flowYes, with that ancestor
fixedThe viewportNoNo — it stays put
stickyIts scroll container, past a thresholdYesUntil it hits the threshold, then stops
"Positioned ancestor" means: the closest parent, grandparent or beyond whose position is anything other than static. If there is none, absolute measures from the page itself. This is why position: relative with no offsets at all is such a common line — it exists purely to become the anchor for a child.
The two that keep their space are the two that stay in the flow: relative and sticky. The two that are lifted out — absolute and fixed — leave a hole behind them, and everything below moves up to fill it.
Part 2 · Position · Live

Scroll this. All five, at once.

The frame below is a real scrollable page. Scroll inside it and watch what each box does — the blue one stays pinned to the frame, the green one sticks and then releases, the others move normally.

Scroll inside the frame, not the slide. The frame is its own viewport, which is exactly why fixed pins to it rather than to your screen.

  • relative — nudged 12px down and right from where it would have sat. Notice the dotted outline showing the space it still occupies.
  • absolute — a badge pinned to the top-right corner of its card. It scrolls away with the card, because it is anchored to the card.
  • fixed — the blue bar. It ignores scrolling completely and stays welded to the frame's viewport.
  • sticky — the green header. It scrolls up normally, hits top: 0, then stops and holds — until its section ends and it is pushed away by the next one.
Point at the sticky one and say this: sticky is not a third thing. It is relative until it reaches the threshold, and fixed afterwards. That is the whole behaviour, and it is the reason it keeps its space in the flow — a fixed header does not, which is why fixed headers need padding on the body to compensate and sticky ones do not.
Part 2 · Position · Live

Break it on purpose — the three gotchas

Each switch below breaks one thing in the live frame. Flip them one at a time and watch the failure happen — every one of these is a bug your learners will file a ticket about within a month.

Gotcha 1 · the escaping badge

Take position:relative off the card and the absolutely-positioned badge flies to the corner of the page. It is not broken — it simply looked further up the tree and found nothing, so it anchored to the page. An absolute child with no positioned parent is the classic "why is it in the wrong corner" bug.

Gotcha 2 · sticky that never sticks

Remove top and position:sticky does absolutely nothing — silently. Sticky needs a threshold to stick at. No error, no warning, it just scrolls away like a normal element.

Gotcha 3 · the killer

Any ancestor with overflow: hidden, auto or scroll silently disables sticky inside it. This is the single hardest position bug to find, because the offending rule is usually three files away and was added for a completely unrelated reason.

Part 2 · Position

z-index only works on positioned elements

  • z-index is ignored on a static element. If your z-index "does nothing", this is almost always why — add position: relative and it starts working. (Flex and grid children are the exception: they accept z-index without being positioned.)
  • A stacking context traps its children. A child with z-index: 9999 inside a parent with z-index: 1 can never rise above a sibling of that parent with z-index: 2. The whole group moves as one.
  • These silently create a stacking context: opacity less than 1, any transform, filter, will-change, and position: fixed or sticky. Adding a hover animation can therefore break a dropdown that worked yesterday.
The cure for the z-index arms race: stop inventing numbers. Define a scale once — --z-dropdown: 100; --z-sticky: 200; --z-modal: 300 — and use only those. z-index: 99999 in a codebase is a confession, not a solution.

Part 3 · Grid

Grid or flexbox? One question.

Flexbox

One direction at a time

You have a set of things and you care how they sit along a line. The items decide their own sizes; the container distributes what is left.

Reach for it when: a navbar, a toolbar, a row of buttons, a card's internal stack, anything where the number of items varies and you just want them arranged sensibly.

Grid

Two directions at once

You have a structure in mind — rows and columns that line up across the whole layout. The container defines the shape; items are placed into it.

Reach for it when: a page skeleton, a photo gallery, a dashboard, a pricing table — anywhere things must align both across and down.

They are not rivals. Real pages use grid for the page skeleton and flexbox inside each region. Grid places the header, sidebar, main and footer; flexbox arranges the buttons inside the header.
Part 3 · Grid

Four declarations cover most of grid

.grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 16px;
}
display: grid
Turns the container into a grid. Children become grid items.
grid-template-columns
Defines the columns. This is the one that does the work.
gap
Space between tracks. Never collapses, never applies to the outer edge.
grid-column
On a child — how many columns it spans.
fr means "one share of the space that is left" after fixed sizes and gaps are taken out. 1fr 2fr gives a third and two thirds. Unlike % it already accounts for the gap, so the row never overflows.

Part 3 · Grid

The one line worth memorising

grid-template-columns:
  repeat(auto-fit, minmax(220px, 1fr));

That is a fully responsive gallery with no media query at all. Read it as an instruction to the browser:

  • minmax(220px, 1fr) — never make a column narrower than 220px, but let it grow to share the space.
  • auto-fit — fit as many of those as will go, then wrap. Recount every time the container resizes.
Why this beats media queries here: it responds to the container's width, not the screen's. Drop the same grid into a narrow sidebar and it reflows correctly — a media query would still be reading the window and get it wrong.
auto-fit vs auto-fill: with few items, auto-fit stretches them to fill the row; auto-fill leaves empty invisible columns and the items stay narrow. Nine times out of ten you want auto-fit.
Resize this window — the columns recount themselves
12345678

No breakpoints were written. The browser is doing the arithmetic on every resize.

The page skeleton, in five lines 
.page {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-rows: auto 1fr auto;
  min-height: 100vh;
}
header, footer { grid-column: 1 / -1; }

1 / -1 means "first line to last line" — full width, whatever the column count is.

Part 4 · Media queries

The anatomy of a media query

The conditions worth knowing

min-width
Applies at this width and wider. The mobile-first direction.
max-width
Applies at this width and narrower. The desktop-first direction.
orientation
portrait or landscape.
prefers-color-scheme
dark — how dark mode is actually built.
prefers-reduced-motion
reduce — switch off animation for users who asked.
print
A media type, not a feature: @media print styles the printed page.
Without this line, none of it works on a phone.
<meta name="viewport" content="width=device-width, initial-scale=1">

Without it a phone pretends to be 980px wide and zooms out, so max-width: 600px never matches and your breakpoints appear to do nothing at all. Check this first, every single time, before debugging anything responsive.

Modern range syntax is now widely supported and reads much better:
@media (width >= 768px)  ·  @media (400px <= width <= 900px)
Part 4 · Media queries

Mobile first — and why the direction matters

Mobile first · min-width 
/* base: the phone. No query. */
.grid { display: grid; gap: 16px; }

@media (min-width: 640px) {
  .grid { grid-template-columns: repeat(2,1fr) }
}
@media (min-width: 1024px) {
  .grid { grid-template-columns: repeat(4,1fr) }
}

Each query adds to the one before. The phone never downloads or parses rules it has to undo.

Desktop first · max-width 
/* base: the desktop */
.grid { display:grid; grid-template-columns: repeat(4,1fr) }

@media (max-width: 1023px) {
  .grid { grid-template-columns: repeat(2,1fr) }
}
@media (max-width: 639px) {
  .grid { grid-template-columns: 1fr }
}

Each query undoes the last. Notice the off-by-one values — 1023, 639 — needed to avoid two rules matching at once.

Why the industry standardised on min-width: the phone is the constrained device. Giving it the simplest stylesheet and adding complexity for bigger screens means the weakest device does the least work — and you never write 1023px.
Order matters, and there is no magic. Media queries add no specificity whatsoever. Two matching rules of equal specificity are settled by source order alone — so a min-width block placed above the base rule it is meant to override will simply lose. Put your queries at the bottom, largest last.
Part 4 · Media queries

Where breakpoints actually come from

Not from a list of phone models. You resize the browser slowly and stop where the design stops looking right — that width is your breakpoint. Devices change every year; the point where three cards stop fitting does not.

1280 +Desktop

  • Three or four breakpoints is plenty for almost any product. If you need seven, the layout is fighting you — reach for auto-fit or clamp instead.
  • Use em in the query, not px. (min-width: 40em) scales with the user's font setting; a px breakpoint ignores it and can trap a large-text user in the phone layout on a desktop.
  • Test between the breakpoints, not at them. Everything looks fine at exactly 768px because that is where you were looking. 900px is where things break.
A complete, realistic breakpoint set 
/* base — phone, no query */

@media (min-width: 40em)  { /*  640px */ }
@media (min-width: 48em)  { /*  768px */ }
@media (min-width: 64em)  { /* 1024px */ }
@media (min-width: 80em)  { /* 1280px */ }
Divide by 16 to convert. 640 ÷ 16 = 40em. The root font size is 16px by default, and that is the number em is measured against inside a media query — always the root, never the element's own font size.
Part 4 · Implementation

One real page, three widths

This is the whole stylesheet for a working responsive layout. Read it top to bottom: it is a phone layout, then two additions.

/* ---------- base: phone ---------- */
.layout {
  display: grid;
  gap: 16px;
  padding: 16px;
}
.nav ul {
  display: flex;
  flex-direction: column;  /* stacked */
  gap: 8px;
}
.aside { order: 2; }   /* below main */

/* ---------- 40em: tablet ---------- */
@media (min-width: 40em) {
  .nav ul { flex-direction: row; }
  .cards {
    grid-template-columns: repeat(2, 1fr);
  }
}

/* ---------- 64em: laptop ---------- */
@media (min-width: 64em) {
  .layout {
    grid-template-columns: 1fr 260px;
    max-width: 1200px;
    margin-inline: auto;
  }
  .aside { order: 0; }  /* back beside main */
  .cards {
    grid-template-columns: repeat(3, 1fr);
  }
}
  • The phone layout has no media query. It is simply the rules at the top. That is what "mobile first" means in practice.
  • Each query only says what changes. The 64em block never repeats gap or padding — those are already inherited from the base.
  • The nav flips direction, not display. flex-direction: column to row is one property, and the gap keeps working in both.
  • order moves the sidebar below the article on a phone and back beside it on a laptop — and here that is legitimate, because the reading order barely changes.
  • margin-inline: auto is the modern margin: 0 auto. It sets only the horizontal margins, so it never fights a vertical margin you set elsewhere.
Notice what is missing: no display:none hiding content from phone users. Hiding is a last resort — a phone user wants the same information, arranged differently.
Part 4 · Media queries

The queries you should write fewer of

Modern CSS solves many responsive problems without a breakpoint at all. Reach for these first, and keep media queries for genuine layout changes.

Instead of font breakpoints 
font-size:
  clamp(1.5rem, 4vw, 3rem);

Fluid between a floor and a ceiling. Replaces three breakpoints with one line.

Instead of column breakpoints 
grid-template-columns:
  repeat(auto-fit,
    minmax(220px, 1fr));

The browser recounts the columns on every resize. No breakpoints to maintain.

Instead of wrapping breakpoints 
display: flex;
flex-wrap: wrap;
/* items: flex: 1 1 220px */

Items wrap when they no longer fit. One declaration, fully responsive.

And the one that changes everything

Container queries

.card-area { container-type: inline-size; }

@container (min-width: 400px) {
  .card { display: flex; }
}

A media query asks how big is the screen. A container query asks how big is the space I am actually in — so the same card component works in a wide main column and a narrow sidebar without knowing where it was placed. Baseline across all major browsers since 2023.

The honest summary to give them: media queries are for layout structure — when the page skeleton genuinely changes shape. For everything else — type size, column counts, wrapping — modern CSS is already responsive, and a breakpoint is usually a sign you reached for the old tool out of habit.
Still required, still not optional: prefers-reduced-motion and prefers-color-scheme. These are media queries that have nothing to do with screen size, and both are accessibility features users have explicitly asked for in their operating system.

What to carry out of this module

  • justify along the main axis, align across it. flex-direction decides which is which — not the words horizontal and vertical.
  • flex: 1 is 1 1 0. The zero basis is why it makes every child equal regardless of content.
  • order changes paint order only. Screen readers and Tab still follow the HTML — so use it for presentation, never for meaning.
  • Absolute is measured from the nearest non-static ancestor. That is what position: relative with no offsets is for.
  • Sticky needs a threshold, and any ancestor with overflow set will silently kill it.
  • z-index is ignored on static elements, and a stacking context traps its children no matter how large their numbers are.
  • Flex for one direction, grid for two. Real pages use grid outside and flex inside.
  • repeat(auto-fit, minmax(220px, 1fr)) is a responsive gallery with no breakpoints.
  • Mobile first, min-width, queries at the bottom. Media queries add no specificity — source order is all you have.
  • Check the viewport meta tag first when responsive CSS "does nothing" on a phone.
